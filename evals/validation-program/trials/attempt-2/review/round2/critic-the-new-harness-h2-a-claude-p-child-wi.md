# Critic lens: The new harness H2 (a claude -p child with its own CLAUDE_CONFIG_DIR, a setup-token token, --plugin-dir, settings.json hooks, --effort, dontAsk, --allowedTools, stream-json and session persistence) and Instruments 1 and 2. The question is whether H2 can be run, isolated and blinded as v1 claims, on Windows 11 with Claude Code 2.1.296 and no API key. I fetched code.claude.com pages live this session (headless, authentication, env-vars, settings-reference, hooks, plugins/loading, plugins-reference, cli-reference, permissions, permission-modes, memory, skills, workflows, sub-agents, tools-reference, claude-directory, agent-sdk/typescript). I checked `claude --version` (2.1.296) and `claude --help`. I read the owner's settings.json and the key names of ~/.claude.json, reading no secret values. I listed `git ls-tree 5886ff7`. I did not run a child session: the task forbids creating files, and a fresh config dir writes some.

Verdict: The docs show nothing that stops H2 from running on Windows 11 with 2.1.296 and a setup-token token. User-scope CLAUDE.md and rules load from CLAUDE_CONFIG_DIR under -p, settings hooks and deny rules apply, --plugin-dir loads hooks and skills, and stream-json and the JSONL carry what the parser needs (H2-12 to H2-16 fail).

Three of v1's claims do not hold as written:
- **Isolation (H2-02, KILLS):** --allowedTools does not restrict the tool set, and read-only Bash and PowerShell commands read outside the cwd past the deny rules. The fix is --tools plus blockReadsOutsideWorkingDirectories.
- **Blinding (H2-04, H2-05):** the loader prints the config directory's path, and the plugin tree ships an answer key, evals/scenarios.md.
- **Capture (H2-01):** a PreToolUse continue:false can truncate a fan-out mid-stream. PostToolBatch is the documented whole-batch stop.

Four smaller problems, each fixable:
- A fresh config dir per session makes every session a first session. Flag-gated tools, Workflow among them, can vary by session, and an inference from the owner's cached flag names suggests streaming tool execution can too (H2-03, H2-11).
- The token's revocation is unverified, and plan usage may be unreadable from inside the child (H2-06, H2-07).
- The exit code of a hook-stopped run is undocumented; key on terminal_reason instead (H2-08).
- The child environment needs an allowlist, not run-eval.sh's denylist (H2-09).

The loader route reproduces the owner's delivery mechanism, not the owner's context (H2-10).

What would change this:
- If I1 shows the token session caches no flags, or lacks Workflow, or lacks `fable` in the Agent model enum, the workflow tasks or the fable tasks leave H2 on a pre-declared branch.
- If I5's 14-call probe shows PostToolBatch does not fire after denied calls, scoring falls back to the first call only.

None of this was run. It rests on documentation plus files I read on this machine.

Note on the no-files instruction: I saved copies of the fetched doc pages under scratchpad/h2docs to quote them verbatim. I wrote nothing else.

## Attacks

### H2-01 [BOUNDS] target: Instrument 1 (v1 line 77: the observer returns continue:false from PreToolUse on every Agent or Workflow call). Scoring set (line 173: every call in the first delegating turn). Probe I5's three-call check.

Attack: A PreToolUse stop can land while the model is still streaming the rest of its message. The hooks page says the stop applies even when the tool call completes while Claude is still streaming. The owner's cached flags include tengu_streaming_tool_execution2=true, which by its name (an inference) means tools start before the message ends. On a fan-out, the observer's continue:false on call 1 can therefore cut off calls 2..n before they are emitted. The 'first delegating turn' then holds a truncated set, and how many calls are lost depends on timing. That decides 'every call' labels (D8, D14, D15) and D2's 14-call fan-out. Three short calls in I5 may finish streaming before the first hook returns, so the probe can pass and the main run still truncate. A separate, smaller point: v1 has all parallel observer processes append to one record file, and the Windows docs Claude Code cites make no promise that concurrent appends are atomic.

Required edit: Split the observer across two events. On PreToolUse (Agent|Workflow) it records tool_input to its own file named <session_id>-<tool_use_id>.json, created with an exclusive flag (no shared append). It returns permissionDecision deny and no continue field. A PostToolBatch hook (no matcher) returns continue:false with the neutral stopReason when the batch's tool_calls include an Agent or Workflow call. It also writes that tool_calls array as the batch record. Register as the cross-check that the batch record equals the transcript's first delegating turn, call for call. Add to I5 a 14-call fan-out in D2's shape. It must check four things: PostToolBatch fires after a batch whose calls were all denied; no assistant message follows the batch; terminal_reason; and in arm D, that the gate and the observer running together still end the session. Pre-declared fallback if PostToolBatch does not fire after denied calls: keep the PreToolUse stop, score the first call only, and make 'every call' labels per-call descriptive.

Evidence: hooks.md (fetched live): 'For `PreToolUse` and `PostToolUse` hooks, the stop applies even when the tool call fails or completes while Claude is still streaming a response.' PostToolBatch: 'Runs once after every tool call in a batch has resolved, before Claude Code sends the next request to the model... `PostToolBatch` fires exactly once with the full batch'; 'Returning `decision: "block"` or `continue: false` stops the agentic loop before the next model call.' Its input carries `tool_calls` with tool_name, tool_input and tool_use_id. 'All matching hooks run in parallel.' Observed today in ~/.claude.json: cachedGrowthBookFeatures.tengu_streaming_tool_execution2 = true. Attempt 1's T03 issued 13 calls in one message (REVIEW-LEDGER CL4).

Checkable: hooks.md says a PreToolUse stop 'applies even when the tool call ... completes while Claude is still streaming a response', and that PostToolBatch fires exactly once with the full batch and can stop the loop before the next model call.

### H2-02 [KILLS] target: Isolation (v1 lines 63 and 65): '--allowedTools Agent Skill Read Glob Grep Workflow' plus 'deny rules for the owner's home and repositories'.

Attack: --allowedTools pre-approves tools; it does not restrict the tool set. The H2 child therefore keeps Bash (Git Bash), PowerShell, Edit, Write, WebFetch, Monitor, ListAgents, SendMessage and the rest. Under the plugin eval, ungranted tools were removed. Read-only Bash commands (cat, grep, find, ls) run in every mode, dontAsk included, even outside the working directories. Read deny rules cover recognized file commands but not `grep -r pattern .` run from the target directory. An unscoped `Read` allow also opens every path on the disk that no deny rule names. So a session can read ~/.claude/rules/delegation.md, the owner's projects/ transcripts (which hold this design) or the scratchpad's PROTOCOL-v1 and labels, in any arm. The isolation claim as written does not hold. Separately, the tool set differs from attempt 1's five tools, so contrasts with attempt 1 shift too.

Required edit: Replace the mechanism. Launch with --tools "Agent,Skill,Read,Glob,Grep,Workflow". Pass --allowedTools "Skill Workflow" only: Agent needs no approval, and reads inside the working directory need none in dontAsk. Reads outside the working directory are then denied by dontAsk itself. Add permissions.blockReadsOutsideWorkingDirectories: true to every arm's settings.json. Keep the deny rules as defense in depth, written in POSIX form (Read(//c/Users/<user>/**)). I1 checks three things: the init tools list is exactly those six names (the pilot saw the delegation tool listed as Task, so confirm the name --tools accepts); a canary Read of an owner file is refused; a canary Glob outside the cwd is refused. Add the reduced tool set to 'Limits stated now' as a departure from the owner's sessions.

Evidence: cli-reference.md, --allowedTools: 'Tools that execute without prompting for permission... To restrict which tools are available, use `--tools` instead.' permissions.md: 'Claude Code recognizes a built-in set of Bash commands as read-only and runs them without a permission prompt in every mode, except as permissions.blockReadsOutsideWorkingDirectories changes for paths outside your working directories. The set includes ls, cat, ... grep, find'. Also: Read and Edit deny rules 'don't apply to a command that reads files without naming them, such as `grep -r pattern .`'. permission-modes.md, dontAsk: 'Claude still runs actions that need no approval in Manual mode, such as file reads inside your working directories and read-only Bash commands'. tools-reference.md permission column: Skill and Workflow 'Yes'; Agent, Read, Glob and Grep 'No'. PILOT-RESULTS problem 5: the init tool list showed `Task`.

Checkable: cli-reference.md says of --allowedTools: 'To restrict which tools are available, use `--tools` instead', and permissions.md says read-only Bash commands run without a prompt in every mode.

### H2-08 [BOUNDS] target: Probe I5 ('what does the result message report'), the failure-handling row 'session ended by observer', and the runner's timeout handling.

Checkable: The Agent SDK result type documents terminal_reason with the value 'hook_stopped', and headless.md does not say which exit code a hook-stopped run returns.
