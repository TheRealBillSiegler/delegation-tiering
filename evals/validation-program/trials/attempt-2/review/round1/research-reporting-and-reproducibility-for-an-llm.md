# Research pillar: Reporting and reproducibility for an LLM-agent experiment (Attempt 2 draft protocol v0, 2026-10-11)

## Questions

### Q1. Does the registered protocol and write-up record the requested model ID and the resolved model ID for every session, and the Claude Code alias-to-ID mapping for the `model` values the orchestrator can name (opus, sonnet, haiku, fable)?

Why here: Anthropic fixes weights per ID, so the ID is a sound pin. But the label-agreement score is computed on an alias the orchestrator names, and in Instrument 1 no worker ever runs, so no resolved worker ID exists unless the alias map is probed. Attempt 1 saw `claude-opus-5` in one session's modelUsage next to `claude-opus-5-5` in 58 and never explained it.

Source: https://platform.claude.com/docs/en/about-claude/models/model-ids-and-versions
Quote: Anthropic does not update the weights or configuration of an existing model ID. When an updated version is available, it ships under a new model ID.

Draft: partly: the Orchestrator model and effort section names `claude-opus-5-5` and `claude-fable-5-1` as flags, but Measurement and Records never require the resolved ID per session or an alias-to-ID table, and no probe covers it.

### Q2. Does the protocol record the date and time of every session, given that the serving stack can change without a new model ID?

Why here: The run spans roughly 500 sessions in batches and an Instrument 2 set. A router, classifier or sampling change mid-run would shift behavior under an unchanged ID, and the program's own README says results expire with the next model release. Date stamps are the only way to test for a within-run break.

Source: https://platform.claude.com/docs/en/about-claude/models/model-ids-and-versions
Quote: Model weights are fixed for a given ID, but the serving infrastructure around the model can change over time. This infrastructure includes components such as the request router, safety classifiers, and sampling logic.

Draft: missing: only the draft's own date is given; no per-session UTC timestamp, batch start/end times or order of batches appear in Measurement or Records. Attempt 1 kept `batch1.start` privately and reported only a clean-up `--since` timestamp.

### Q3. Are the exact prompts, rule texts and every instrument text shared verbatim and content-hashed (task prompts, the five rule variants, the skill, the hooks-free plugin variant, the observer hook source and its denial string, the fixture generator output)?

Why here: The trial's whole contrast is text. P, R-, R and the skill-only plugin are generated by string surgery with asserted diffs, and the observer's denial text could itself steer arm D. A reader cannot audit a contrast without the bytes that were delivered.

Source: https://arxiv.org/html/2405.14782
Quote: If possible, full evaluation code including the full prompts used should be provided for reproducible evaluation runs.

Draft: partly: the task table is verbatim and R is 'read at generation time and hashed, as in attempt 1'; P, R-, the skill tag, the variant plugin tree, the observer plugin, the fixture and the generated case directory have no stated hash or manifest.

### Q4. Are randomness controls stated, including what cannot be controlled?

Why here: An audit of 55 pipeline papers found most omitted them. Here the sampling parameters of a headless `claude -p` child are not settable, and run order, concurrency (-j) and shuffle seed all move which sessions share rate-limit or serving conditions. 'Seed recorded' for the bootstrap does not cover any of that.

Source: https://aclanthology.org/2026.acl-short.22/
Quote: We find that randomness controls are missing in 75% of papers and intermediate execution traces in 61%

Draft: partly: Endpoints says the bootstrap seed is recorded and Blinding says the case shuffle has a recorded seed; the draft is silent on sampling parameters being uncontrollable, on run order, on -j, and on whether the same seed (20261009 in attempt 1) is reused for shuffle and bootstrap.

### Q5. Are run-to-run variance and range reported per cell, not only task-level means with an interval over tasks?

Why here: Temperature 0 does not give determinism, and the design uses two runs per cell. A reader needs to see whether the two runs of a cell agree before trusting a mean taken over tasks, and the open question 4 about non-independent runs is only answerable from per-run values.

Source: https://arxiv.org/html/2408.04667v5
Quote: We encourage reporting maximum-minimum scores across runs to have a more robust comparison of models.

Draft: partly: Endpoints and the power simulation use attempt 1's pilot variance, and per-task tables are 'descriptive only'; no requirement to publish both runs per cell or a within-cell disagreement rate.

### Q6. Is the number of independent runs justified against published guidance, and are variance estimates required in the write-up?

Why here: Two runs per cell is far below the figure one agentic-eval paper gives for small effects. The registered protocol should say what effect size two runs can detect and report that as a limit, not only as a power claim for one assumed effect.

Source: https://arxiv.org/html/2602.07150
Quote: Detecting a 2% improvement at p<0.05 with 80% power requires approximately 9 runs per agent under test

Draft: partly: Size, batches and stopping gives a power simulation for endpoint 2 under a 0.3 to 0.8 shift on half the divergent set; it does not state the minimum detectable effect for endpoints 1 and 3 or for the secondary family.

### Q7. Is the protocol frozen in a way a third party can verify (content hash with stated normalization, commit, external timestamp), and does the freeze cover the analysis code, the generators and the probe results?

Why here: Attempt 1 hashed PROTOCOL.md over LF line endings and verified it in the generator. Attempt 2 adds probe outcomes that change arm routes, a power simulation and 'analyze-full.js extended'; any of these edited after data would void the pre-registration without a visible trace.

Source: https://help.osf.io/article/330-welcome-to-registrations
Quote: a frozen version of your project that can never be edited or deleted.

Draft: partly: the draft says 'registered protocol' and a tag will pin the plugin; it does not state the hash procedure, the commit that includes the analysis script and generators, or that probe results are part of the frozen text. The status line says 'not registered'.

### Q8. Is it stated whether the plan uses existing data, given that the probes and attempt 1 data shaped the predictions and the divergent set?

Why here: The predicted unaided choices come from the author's reading of the skill and of attempt 1's B arm, and about twelve probe sessions run before registration. Those are existing data the design is conditioned on, and a reader must be able to separate them from the confirmatory data.

Source: https://www.cos.io/initiatives/prereg
Quote: You must state whether the plan uses existing data, along with the related certifications.

Draft: partly: the Limits section says the predictions are the author's reading and are tested by A0 and P; the draft does not label attempt 1 and probe sessions as existing data or list which probe outputs are written in.

### Q9. Are deviations and post-hoc analysis choices disclosed in a form that separates confirmatory from exploratory results?

Why here: Attempt 1 logged twelve numbered deviations and stated that two scoring readings (omitted effort scored as the session level, the workflow role rule) decided most of the effort result. Attempt 2 pre-registers those rules, which is the right fix, but the draft still has no deviation template or exploratory label.

Source: https://www.cos.io/initiatives/prereg
Quote: Analyses changed after initial results are seen should be labeled exploratory.

Draft: partly: Records ends with 'Every deviation is recorded with its reason' and Limits confines prediction failures to a sensitivity analysis; no required fields (date, who knew what, effect on denominators) and no exploratory label.

### Q10. Are exclusion and failure-handling rules registered before the data: timeouts, harness errors, observer failures, sessions that never delegate, sessions where the model stops after a denial, and missing cells?

Why here: Attempt 1 excluded five timeouts after the fact (its deviation 7, 'the protocol is silent'), left 17 sessions unstarted and lost both cells of T20. Attempt 2's observer ends sessions on a denial, so 'no observer record' and 'no delegation' become distinct failure modes whose treatment can move a rate.

Source: https://www.cos.io/initiatives/prereg
Quote: The level of detail should be enough for an interested reader to be able to replicate the methods of the original study.

Draft: missing: Measurement scores a non-delegating session as a non-match and Size says harness errors under one quarter pass a health check; no table of failure reason to treatment, no rule for retrying a failed session, and no rule for a cell with no valid run.

### Q11. Can a reader tell how many sessions were launched, scored and excluded, by reason, per arm, and which task cells are empty?

Why here: With about 500 sessions and a sign-flip test over tasks, an empty cell silently drops a task from a contrast (attempt 1 left 13 of 20 tasks with both cells). The write-up must show the denominator for each endpoint.

Source: https://arxiv.org/html/2411.00640
Quote: We suggest including the cluster count alongside the question count when reporting cluster-adjusted standard errors

Draft: partly: Endpoints names the tasks in each contrast ('all 23 scored tasks', 'the divergent set'); Records requires no flow table or per-endpoint count of tasks with both cells.

### Q12. Is the case-to-arm key protected in a way that supports blinding now and an audit later (a hash committed at freeze, the key released with the write-up)?

Why here: Both attempts keep the key outside the repo and unhashed. An outside reader cannot tell that the key existed before the data or that arms were not reassigned after seeing results.

Source: https://help.osf.io/article/330-welcome-to-registrations
Quote: posting a time-stamped, read-only version of your study plan to a public repository

Draft: partly: Blinding says opaque names, a recorded seed and a key 'outside the repo'; no commitment hash and no promise to publish the key afterwards.

### Q13. Are per-sample outputs shared, so aggregates can be recomputed without the raw transcripts?

Why here: The draft and attempt 1 both release 'aggregates only'. That leaves no way to check a rate, a mean difference or a Holm adjustment, and it conflicts with the field's basic advice to provide outputs. Instrument 1's output is small (one tool input per session), so releasing it costs little.

Source: https://arxiv.org/html/2405.14782
Quote: sharing outputs can allow results on API models to be reproduced to some extent.

Draft: missing: Records sends raw results, observer records and transcripts to the private directory and the repo gets 'generators, the analysis script, the protocol, and aggregates'.

### Q14. Are costs recorded in the units that matter (token counts by model and class, plus the price table used and its date), given that the owner is on plan usage and costUsd is a list-price estimate?

Why here: Attempt 1 labelled costUsd 'list-price estimates, not billed usage' that may exclude background workers. Pricing differs by model and by cache class, so a dollar figure is not recomputable without the token breakdown and the price table.

Source: https://platform.claude.com/docs/en/about-claude/models/overview
Quote: Batch API requests are 50% off; prompt cache reads cost 10% of the base input price (2.5% on Claude Fable 5.1 and Claude Mythos 5.1, 5% on Claude Opus 5.5 and Claude Sonnet 5.5).

Draft: partly: Size, batches and stopping sets list-price ceilings and reports sessions as a multiple of attempt 1; Measurement adds `costUsd` for Instrument 2 only and names no token fields or price table.

### Q15. Does the write-up give a way to validate the code-only parser, such as an independent second implementation or a released sample of labelled records?

Why here: Every score is applied by code. Attempt 1's one strong check was 638 of 638 agreement between the harness graders and its parser. The draft removes graders from the main run in favour of the observer, so that cross-check disappears unless it is kept.

Source: https://crfm-helm.readthedocs.io/en/latest/reproducing_leaderboards/
Quote: find the appropriate `run_entries_*.conf` and `schema_*.yaml` files

Draft: partly: Measurement says rules are 'applied by code, never by a judge'; it does not keep a second instrument for the first-delegation read or name a released validation set.

### Q16. Does the protocol record the execution environment: Claude Code version, OS, Node version, effort route and stamped level, permission mode, harness flags, removed environment variables, and plugin versions of the helper plugin?

Why here: Attempt 1 showed the child's Agent tool schema lost `effort` at `xhigh` on 2.1.295, and the draft's probes I1 to I4 decide routes by version-specific behavior. Without the full environment a reader cannot tell whether a different build would reproduce.

Source: https://aclanthology.org/2026.acl-short.22/
Quote: including prompts, judge configurations, retrieval snapshots, and intermediate traces

Draft: partly: Harness cites Claude Code 2.1.296 and the effort routes, and the mediators include the effort stamp and the Agent tool definition's `effort` presence; OS, Node, helper-plugin hash, permission mode, stripped variables and the raw command lines are not required.

### Q17. Should the public bank carry a canary string, and does the published material (prompts, labels, predictions, fixture generator) risk contaminating future model training and so invalidating a re-run?

Why here: The trial measures whether text transmits a ladder. If the labels, predicted answers and fixture are scraped into a later model, a re-run on that model tests memory, not transmission. This is a modest risk but cheap to flag.

Source: https://github.com/google/BIG-bench/blob/main/docs/doc.md
Quote: All task files should include this string to help avoid training on benchmark data when using web scraped training data.

Draft: missing: Blinding, leakage and records covers leakage into the orchestrator's context, not publication-side contamination.

## Recommendations

1. [must] (Records (new subsection: Provenance manifest, registered)) Add a manifest file, hashed into the frozen protocol, listing SHA-256 of: PROTOCOL (LF-normalized, procedure stated), every generated prompt.md, all five rule texts (P, R-, R, F, A0 empty), the 0.1.2 skill and the hooks-free variant tree, the helper observer plugin including hook source and denial string, the fixture generator output (tree hash), labels.json, the generators and the analysis script. Record the git commit and an external timestamp (a pushed tag).
   Rationale: The contrast is made of bytes. OSF treats a registration as frozen and a reader can only verify that with hashes; attempt 1 hashed only the protocol and the steering text. The draft's 'a tag will pin it' is not yet a verifiable procedure.

2. [must] (Measurement (new: per-session record schema)) Require for every session: UTC start and end time, batch, run index, case name and arm (key-joined), requested model, resolved model ID from the init message and modelUsage, Claude Code version, stamped session effort per turn, whether the Agent tool definition carried `effort`, harness flags, exit status, turns, input/output/cache tokens by model, costUsd, and the observer and gate decisions. Add a probe that maps each `model` alias the Agent tool accepts to the resolved ID.
   Rationale: Anthropic fixes weights per ID but says serving infrastructure can change, so dates and resolved IDs are the audit trail for a within-run break. Instrument 1 runs no worker, so the alias map has to be probed. Attempt 1's unexplained `claude-opus-5` shows resolved IDs can surprise.

3. [must] (Measurement (exclusions)) Register a failure-handling table before data: harness error, timeout, missing observer record, session ends with no delegation, model stops after a denial, malformed Workflow script, empty cell. For each, state treatment (excluded, scored non-match, retried once with the same seed and case), the denominator affected, and the sensitivity run that keeps it. Report a flow table per arm: launched, scored, excluded by reason, tasks with both cells per contrast.
   Rationale: Attempt 1 decided timeout exclusion after the fact and lost cells unevenly. A pre-registered rule removes a researcher degree of freedom, and a flow table lets a reader see each endpoint's actual n.

4. [must] (Records (publication of per-session rows)) Publish a de-identified per-session rows file (opaque session id, task, arm, run, batch, timestamps, parsed first-delegation model/effort/fork/Workflow site list, every score and mediator, token counts, cost, exclusion status) together with the analysis script, so every reported number is recomputable. Publish the observer's captured tool inputs (Agent input or Workflow script text) as they are short and the tasks are synthetic.
   Rationale: Field guidance is to provide model outputs, and aggregates alone cannot be checked. The rows are the smallest artifact from which each endpoint, Holm adjustment and bootstrap (with the recorded seed) can be reproduced.

5. [must] (Records (withholding policy)) State what stays private and why: raw session JSONL transcripts, subagent JSONL, temp directories and plugin ledgers (they carry local paths, account and session identifiers, environment and, in arm F, the owner's full CLAUDE.md and rule files), the author's `.claude` configuration, and anything read from the owner's machine outside the fixture. State what is released: generators, fixture, prompts, arm texts, hooks, parser, rows, observer records, aggregates, deviations. Publish a SHA-256 list of every withheld transcript file, taken before any redaction, with the record count.
   Rationale: Hashes let the owner later prove, to an auditor under access, that the rows came from specific files, without exposing the files. Withholding by named class with a reason is auditable; withholding by default is not. Arm F's inputs are private by construction and should be summarized, not released.

6. [should] (Blinding, leakage and records (key)) Commit a salted SHA-256 of the case-to-arm key in the frozen protocol and commit to publishing the key with the write-up. Record the shuffle seed and use a different seed for the bootstrap, or state they are equal.
   Rationale: Lets an outside reader confirm the arm assignment pre-dated the data. Neither attempt hashed the key. The salt prevents guessing the key from its small space.

7. [should] (Measurement (parser validation)) Keep a second, independent read of the first delegation in the main run: for sessions where a transcript is available, compare the observer record with a transcript parser, and report agreement. Release a small set of redacted labelled records (including denied calls, Workflow scripts and a no-delegation case) as parser test fixtures.
   Rationale: All scores are code-applied; attempt 1's 638 of 638 grader/parser agreement was its only validity check on the instrument, and the draft's capture-and-stop design would otherwise drop it. Also gives an answer to open question 1 about the observer.

8. [should] (Randomness and repetition (Endpoints and Size)) Add a paragraph stating that sampling parameters of the headless child are not controllable, that outputs are non-deterministic at any setting, and recording run order, concurrency and seeds. Require publishing both runs for every cell and a within-cell disagreement rate. State the minimum detectable effect for each primary endpoint at two runs, not only the endpoint-2 power case.
   Rationale: Repeated-run studies show single numbers hide instability and recommend reporting range and variance. Two runs per cell is small against the nine-run figure given for a 2% effect, so the limit should be quantified in the registered text.

9. [should] (Records (deviations and existing data)) Add a deviation-log template (number, date, discovered when, what the analyst had seen, change, effect on denominators, confirmatory or exploratory) and a statement that attempt 1 and the probe sessions are existing data. List which probe outputs are written into the registered text and publish the probe transcripts' derived rows.
   Rationale: OSF requires saying whether existing data are used and expects most studies to deviate; changes after seeing results are exploratory. The probes decide routes (loader, effort, observer), so they shape the confirmatory design.

10. [should] (Measurement (cost)) Record token counts by model and cache class per session, the price table and its fetch date, and the cost method (list-price estimate, not billed usage, workers possibly excluded). Report plan-usage observations separately: rate-limit pauses, stopped runs, wall-clock gaps between batches.
   Rationale: Cost depends on cache pricing that varies by model, and the owner pays in plan usage, so dollars are not recomputable or comparable unless the token classes are published. Attempt 1 did flag the caveat; the draft should make it a field.

11. [should] (Harness (environment record)) Require recording the Claude Code build, OS version, Node version, permission mode, the exact command lines for each invocation, the list of environment variables removed or added, and the hash of the helper plugin. Add an environment-capture step to each batch's health check.
   Rationale: Routes were decided by version-specific behavior (the `effort` parameter disappearing at xhigh on 2.1.295). A reader on another build needs to know what to match.

12. [should] (Limits stated now (reporting rows)) Add a limit that the rows reproduce the scores but not the tool-use trace before the first delegation (files read, turns), since transcripts stay private; publish those mediators as derived columns. Add the sentence that the result is valid for the dated model IDs and Claude Code build recorded, and expires with the next release.
   Rationale: ReproEvalCard-style reporting names intermediate traces as a needed artifact; with the transcripts private, the derived mediator columns are what a reader gets. The README already promises expiry; the protocol should repeat it.

13. [consider] (Blinding, leakage and records (publication-side contamination)) Put a canary string in the published task bank, labels and fixture generator and note that a re-run on a later model may be contaminated by the public predictions and labels.
   Rationale: A canary is the common cheap signal for scraped benchmark data; the risk here is small but it affects re-runs, which the program says expire anyway.

14. [consider] (Endpoints (reporting)) For each endpoint report the number of tasks, sessions per cell, the paired difference, its standard error or bootstrap interval, the permutation p, and the Holm-adjusted p, in one table, and add task-level paired differences as a released file.
   Rationale: Paired-difference and count reporting is what lets a reader recompute an interval from the rows; attempt 1's results table already did most of this and should be the template.

## Gaps

- Could not read the full ReproEvalCard checklist or the GUIDE-LLM checklist. The ACL page gave only the abstract (the preview URL returned 404) and GUIDE-LLM appeared only in a search snippet, so I did not check item wording. My item list is assembled from several sources, not from one published checklist.
- No Inspect reproducibility page exists at the URL tried (404). The Inspect eval-logs page documents eval details, plan, stats, request ids, run-config export and sample ids, but does not confirm that a git revision, package versions or seed are logged. I make no claim about what Inspect records beyond that.
- The lm-evaluation-harness interface page covers --seed, --log_samples and --show_config but says nothing about prompt hashes, task versions or git hashes. The 'task and codebase version is a de facto reporting standard' statement is from the Lessons from the Trenches paper, relayed by a summarizer.
- The HELM output file names (scenario_state.json, run_spec.json, per_instance_stats.json) come from search-result text, not from a page I fetched in full. The HELM reproduction page I fetched does not say whether per-instance outputs are released. HELM's own home page returned only a title.
- I found no published standard for how to report repeated-run LLM or agent experiments; the repeated-run quotes come from two papers read through their HTML versions (the PDFs were unreadable). Treat the nine-run figure as one paper's result for its setting, not as a norm for this design.
- I found no source on hash commitments for withheld data or on transcript redaction. The recommendations on the salted key hash, the transcript hash list and the withholding classes are my reasoning, not a cited practice.
- Quotes come through WebFetch's summarizer and may be lightly edited; each should be checked against the page before it is cited in the protocol. I did not re-fetch Claude Code documentation on what a transcript or the init message records; statements about resolved IDs, the effort stamp and modelUsage rest on FACTS.md and attempt 1's FULL-RESULTS.md. I did not read attempt 1's PROTOCOL.md Records and Measurement sections beyond what grep returned, nor PILOT-RESULTS.md in full.
- I did not verify that attempt 1's private data directory holds the items it says (key, rows, transcripts), and I could not check whether `claude-opus-5` in one attempt-1 session was an orchestrator, worker or alias artifact.
