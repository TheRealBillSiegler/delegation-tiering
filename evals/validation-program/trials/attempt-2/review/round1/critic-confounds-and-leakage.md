# Critic lens: confounds and leakage

Verdict: As written, the protocol cannot give a credible answer to question 1 or question 4. The placebo is a pair of path-scoped rules that, under the loader, do not load at session start the way R does. The belief arm removes the gate claim and the ladder pointer together, and its naming endpoint is already at ceiling. Question 2 can change a decision about the skill if the bounds are applied: one plugin path name across arms, a case root outside the repo, a renamed fixture, paraphrase twins with independent labels, and a decision rule that requires the skill to have been read. Without them, a positive RS minus R is partly lexical lookup on the author's phrasing, and a null may only mean the skill went unread at the chosen effort. For the gate, Instrument 1's D arm is an A/A copy of RS by construction, so only Instrument 2 bears on it, and there the allow-path reminder has to be separated from denials.

## Attacks

### CL1 [KILLS] target: Arms: P (placebo text), and the limit "the placebo matches the rule's length and route"

Attack: P does not match R's route or dose under the loader, which is the route the draft prefers. Both placebo files carry `paths:` frontmatter, and the delegation rule has none. Path-scoped user rules do not load at session start. This reviewing session's own session-start block loaded delegation.md, coding-principles.md, git-hygiene.md, propose-dont-apply.md, reasoning-posture.md and analysis-doc-voice.md, but not markdown.md or docstrings.md. So in P the orchestrator starts with only four table lines. docstrings.md never loads, because the fixture is Node. markdown.md loads mid-session, and only in sessions that read a .md file before delegating. The draft's premise that these are rules "whose paths no task touches" is false: T01, T03, T04, T05, T07, T21, T22 and T25 all name .md files. P's exposure therefore varies with the task and with the orchestrator's reads before delegating, so R minus P mixes content with dose and timing. Under append_system_prompt the failure flips. The frontmatter becomes literal text, and the rows say the rule loads "only when touching *.md" while the text is already present, a framing R does not have. Two sub-attacks fail. P is inert: line-wrapping and docstring mood have no path to a tier choice. The rows leak nothing: they hold no agent, model, effort, tier or delegat strings, and lines 7 and 8 are shared with R.

Required edit: Replace P with session-start text that has no `paths:` frontmatter. One option is `~/.claude/rules/coding-principles.md` (69 words, no frontmatter, CLAUDE.md line 14 says "session start", none of the banned strings) with its row. The other is a synthetic rule of matched length on an unrelated topic. Add a canary to the placebo file in probe I1 to show it arrives at session start in the same position as R. Residual risk to state: coding-principles' TDD sentence could lengthen T11's spec. Endpoint 1 is a naming rate, so that is tolerable.

Evidence: ~/.claude/rules/markdown.md lines 1-5: `paths: - "**/*.md" - "**/*.mdx"`. docstrings.md: `paths: - "**/*.py"`. delegation.md line 1 is `# Delegated-agent model rule`, with no frontmatter. PROTOCOL-v0 line 50: "Both are path-scoped rules whose paths no task touches." Task table, lines 106-130. CLAUDE.md lines 13 and 15: "only when touching `*.md`" and "only when touching `*.py`".

Checkable: A session started with the owner's ~/.claude/rules shows delegation.md and coding-principles.md in its session-start instruction block, but not markdown.md or docstrings.md. Check the orchestrator's own session-start context, or run probe I1 with a path-scoped canary.

### CL2 [KILLS] target: Arm R− and the Belief decision rule (question 4)

Attack: The rule file makes no gate claim. The only gate claim is CLAUDE.md line 16's "(skill + PreToolUse gate)" with "every Agent and Workflow call". R− deletes that claim, and it also deletes the rule's "Tier ladder and rationale: the delegation-tiering skill (delegation-tiering plugin)." That sentence tells the model a ladder exists. R minus R− therefore moves gate belief, the ladder pointer and about 25 words of length at once. On named-model rate, both arms keep "gets an explicit `model`" and "Never inherit the session model silently", and attempt 1's text arm named a model 13 of 13. The belief contrast sits at that ceiling and cannot show deterrence. On model agreement, the gate never checks the tier, so the likelier cause of any difference is the ladder pointer, yet the decision rule credits the gate. One sub-attack fails: the remaining text does not imply enforcement, because "Never" is a prohibition, not a claim that something checks. The decision rule also overreaches. A clean belief effect belongs to the sentence, which works whether or not the hook exists, so it shows nothing about "the gate's deterrent value". Attempt 1's text-only arm made no visible search for the missing skill before delegating (10 of 15 sessions delegated with no prior tool call). Any effect of the pointer would therefore sit in reasoning the listed mediators cannot see.

Required edit: Manipulate the gate claim alone. R−gate is R with "PreToolUse gate" and "every Agent and Workflow call" removed from the row, keeping the skill pointer in both the rule and the row. Test belief where naming is not at ceiling: add two or three tasks that invite omission (for example, "spawn a quick subagent on the default model to ...") and score them on named-model rate. Reword the belief decision rule so the effect is attributed to the sentence. It bears on keeping the hook only if the sentence would be deleted along with the hook.

Evidence: delegation.md is a single paragraph with no gate, hook or PreToolUse string. CLAUDE.md line 16. PROTOCOL-v0 lines 49 and 168. FACTS line 48: B named a model 13/13. Attempt-1 batch-1 B-arm transcripts show no skill or plugin search before the first delegation.

### CL4 [BOUNDS] target: Instrument 1: "On the first matching call it writes the tool input ... and returns a deny"

Attack: "The first matching call" assumes one call per delegation, but shape tasks emit several calls in parallel. Attempt 1's T03 put 13 Agent calls in one assistant message in all four arms. The draft's T03 has 14 files, and T12 asks for three reviewers. Each sibling call's PreToolUse hook runs as its own process, so which call counts as "first" is decided by process scheduling. The draft also does not say what the observer returns for the sibling calls. If it allows them, workers run, and in D the gate's allow-path reminder lands. If it denies them, the record still holds one arbitrary call. T12's label is "sonnet; high, each", so an orchestrator that tiers its lenses unevenly gets a random score.

Required edit: The observer denies every Agent and Workflow call and appends each input with its assistant message id, using an atomic append. The scored unit becomes the set of calls in the first delegating assistant message: agreement requires every call in the set to agree, and per-call rates are reported beside it. Extend probe I5 with a parallel-call prompt and verify that every sibling is recorded and denied.

Evidence: Attempt-1 batch-1 transcripts: T03 has 13 Agent calls, all in the first assistant message, in A, B, C and D. PROTOCOL-v0 line 66. Task rows T03 and T12.

Checkable: In attempt-1 batch 1, every T03 session issued all 13 Agent calls in a single assistant message (the same message.id).

### CL5 [BOUNDS] target: Arm D under Instrument 1, the secondary "D minus R", and Instrument 2's gate contrast

Attack: Since no hook output precedes the first call (CL3), D and RS show identical context up to the measured call under Instrument 1. D minus RS there is null by construction. The secondary "D minus R, model agreement" is therefore RS minus R plus noise, counted a second time in the Holm family. In Instrument 2, R runs with no plugin while RS and D load one. Attempt 1 showed the harness builds the child's command line differently when a plugin is listed: the deny list hit ENAMETOOLONG only in the plugin arm. So R differs from RS and D in harness conditions, not only in the skill. On every allowed call in D, the gate's allow path also injects "confirm it is the lowest sufficient for this task; consult the delegation-tiering skill if unsure". Instrument 2's D minus RS on the final delegation therefore mixes the deny path with a prompt to reconsider. There were 0 orchestrator-level denials in 103 earlier sessions, so any movement is likelier to come from the reminder than from a denial.

Required edit: Instrument 1: either drop D (50 sessions) or pre-register D minus RS as an A/A leakage check with an expected null, where a nonzero result flags a leak such as a plugin-path difference. Remove "D minus R" from the Instrument 1 secondary family. Instrument 2: load the observer in record-only (always-allow) mode in all three arms so the plugin footprints match. Count re-dispatches after an allow-path reminder separately from re-issues after a denial.

Evidence: hooks-0.1.2.json. FACTS line 43 (reminder text). FULL-RESULTS deviation 2. PILOT: 0 first-call denials in 40 sessions. FULL-RESULTS: 0 orchestrator-level denials in 63.

Checkable: FULL-RESULTS.md deviation 2 states the ENAMETOOLONG failure hit the plugin arm of both smoke cases while the no-plugin arms ran.

### CL11 [BOUNDS] target: Delivery route: probe I1 and the append_system_prompt fallback

Attack: Within one route the arms are comparable. Across routes they are not, and the draft leaves three seams. (a) I1 may pass only partly: CLAUDE.md loads but the rule file does not, or unscoped rules load but path-scoped ones do not. The draft has no rule for that case, and mixing routes would split R's two parts across positions. (b) The loader wraps instruction text in a system-reminder headed "Codebase and user instructions are shown below ... IMPORTANT: These instructions OVERRIDE any default behavior and you MUST follow them exactly as written". That wrapper is how this reviewing session received the owner's rules. append_system_prompt instead places bare text at the end of the system prompt, after the skill listing. The wrapper is a compliance amplifier, so effect size, skill invocation rate and run-to-run variance can differ by route. The power simulation uses attempt 1's append-route variance. (c) A0 and S have no CLAUDE.md, so they get no wrapper. P controls for the wrapper only once it is route-matched (CL1).

Required edit: All text arms use one route. If I1 passes only partly, every arm uses append_system_prompt. Capture the child's first user message in I1 to record whether the wrapper is present. Do not compare effects across attempts. Rerun the power simulation after the probes using variance from the chosen route, or state attempt 1's variance as an assumption.

Evidence: This reviewing session's own session-start block, which shows the wrapper header. PROTOCOL-v0 lines 26, 82, 177 and 193. FULL-RESULTS assumption that append_system_prompt reached the with-text cases.

Checkable: Probe I1's child transcript will show whether loader-delivered CLAUDE.md and rule text arrive inside a system-reminder carrying the 'OVERRIDE any default behavior' header. Reading the probe's session JSONL settles it.
