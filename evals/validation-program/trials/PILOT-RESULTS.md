# Phase 2 pilot results: with/without trial of the delegation-tiering plugin

This is a pilot of the instrument, not a verdict. It measures what a session costs, how much runs vary, and whether the harness and graders work. Every denominator below is small (10 runs per setup), so the confidence intervals are wide and nothing here supports a claim about the plugin's effect.

## What was run

- Claude Code 2.1.295, `claude plugin eval`, plugin under test at 0.1.3 (worktree `delegation-tiering-validation`, branch `eval/validation-program`).
- Orchestrator pinned with `--model claude-opus-5-5`. The child's init message reports `claude-opus-5-5`, and `modelUsage` in the results shows the same ID.
- Suite: 10 cases, 5 tasks times {nowords, words}, generated by `make-cases.js` into `cases/`. A `nowords` case's arms are C (with plugin) and A (without); a `words` case's arms are D (with plugin) and B (without). `max_turns: 15`, `timeout_seconds: 900`, `allowed_tools: [Agent, Skill, Read, Glob, Grep]`.
- Steering text (words cases only) is `~/.claude/rules/delegation.md` verbatim plus lines 7, 8 and 16 of `~/.claude/CLAUDE.md` verbatim, read at generation time by `make-cases.js` and delivered through `append_system_prompt`.
- Graders: eight `tool_used` graders on Agent, all `arm: both` (delegated, named-model, no-modelless-call, tier-haiku, tier-sonnet, tier-opus, tier-fable, effort-set). No judge graders, so no judge cost.
- Two full-suite invocations (`pilot1`, `pilot2`), `--runs 1` each: 2 times 20 = 40 sessions. They ran one after the other, each with `-j 4`.

Commands (all through `run-eval.sh`, which removes the session variables with `env -u`, then adds the fixed flags; the long invocations ran in the background and were polled):

```bash
# fixed part, from run-eval.sh
env -u CLAUDECODE -u CLAUDE_CODE_CHILD_SESSION -u CLAUDE_CODE_ENTRYPOINT -u CLAUDE_CODE_SESSION_ID \
    -u CLAUDE_CODE_MESSAGING_SOCKET -u CLAUDE_CODE_MESSAGING_TOKEN -u CLAUDE_CODE_SESSION_ATTENDED \
    -u CLAUDE_PID -u CLAUDE_CODE_EMIT_STARTUP_TIMING -u CLAUDE_CODE_QUESTION_PREVIEW_FORMAT -u CLAUDE_EFFORT \
  claude plugin eval . --model claude-opus-5-5 --no-publish --trust-plugin --threshold 0 \
    --json <out>/aggregate-result.json --output-dir <out> --keep-temp -j 4 --max-cost-usd 8 "$@"

# pilot invocations (cwd = the plugin worktree)
./run-eval.sh pilot1 --runs 1 --eval-dir evals/validation-program/trials/cases
./run-eval.sh pilot2 --runs 1 --eval-dir evals/validation-program/trials/cases

# analysis
node analyze-pilot.js collect <result-dir>...      # copies the kept transcripts out of %TEMP%
node analyze-pilot.js report  <result-dir>...      # prints the report below
```

`CLAUDE_CODE_SUBAGENT_MODEL`, `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` and `ANTHROPIC_MODEL` were confirmed unset in the launching shell. `--eval-dir` is required, not optional: `trials/diag/` and `trials/instrument-cases/` also contain `prompt.md` files, so a bare `claude plugin eval .` from the plugin root would load them as cases too. The existing `evals/` content (contract fixtures, `README.md`, `scenarios.md`, the other validation-program directories) contains no `prompt.md` or `case.yaml`, so it is not read as cases.

Raw JSON, HTML reports, stdout/stderr and the copied per-run transcripts are under `$VALIDATION_DATA/trials/` (one directory per invocation; `runs/<case>/<arm>-<n>/` holds `out/trace.jsonl`, the session JSONL, subagent JSONL plus `.meta.json`, and the plugin ledger). `pilot-rows.json` there holds the parsed per-run rows.

## Answers to the instrument questions

1. **Does CLAUDE_EFFORT reach the eval child and set its effort? No.** The docs (env-vars page) describe `CLAUDE_EFFORT` as an output variable that Claude Code sets in Bash subprocesses and hook commands to the effort in effect; the input variable is `CLAUDE_CODE_EFFORT_LEVEL`. A diagnostic plugin (`trials/diag/plugin`) logged the effort a PreToolUse hook sees inside the child. With `CLAUDE_EFFORT` unset the hook saw `medium`; with `CLAUDE_EFFORT=xhigh` it still saw `medium`; with `CLAUDE_EFFORT=low` it still saw `medium` (the child overwrote the variable with its own level). With `CLAUDE_CODE_EFFORT_LEVEL=xhigh` the hook saw `xhigh`, so that variable does cross the isolation boundary and is honored. Per the instruction, the pilot ran with `CLAUDE_EFFORT` unset, so **the orchestrator ran at the default effort, which is `medium` for claude-opus-5-5 in this harness**, not the owner's xhigh. An xhigh pilot would need `CLAUDE_CODE_EFFORT_LEVEL=xhigh` (the `EXTRA_ENV` hook in `run-eval.sh` supports it); I did not run one.
2. **Does tool_used count a call a hook denied? Yes.** A probe case (`instrument-cases/denied-probe`, 3 runs, plugin loaded) told the orchestrator to omit `model`. All 3 first calls were denied by the gate ("Agent call has no explicit model"), and the orchestrator then stopped rather than re-issue. The graders still reported `delegated` as passed ("Agent called 1x") and `no-modelless-call` as failed ("Agent called 1x (expected 0..0)"), with zero allowed Agent calls in the transcript. In the pilot, the grader verdicts matched a parser that counts every Agent call in the transcript in 320 of 320 comparisons, denied calls and calls made by workers included.
3. **Does `--allow-tools Workflow` make the Workflow tool available? Yes.** The child's init tool list gained `Workflow`; the probe case (`instrument-cases/workflow-probe`, one run, `--ablation none`) called it once with a script containing one `agent()` call with `model: 'haiku'`, and the workflow worker ran on `claude-haiku-5-5`. The eval session ended after one turn because the workflow ran in the background, so the run does not show the workflow's result being relayed. Workflow is not in the main suite.

Also verified: `append_system_prompt` reaches both arms (a canary case with `PELICAN-7` was recovered in the with-arm and the without-arm), and `add_dirs` grants worker subagents read access.

## Observations the numbers support (small n, descriptive only)

- Setup A (nothing) never named a model: 0 of 10 first calls had a `model` key, every worker inherited `claude-opus-5-5`, and it never set effort. Setups B, C and D each named a model on 10 of 10 first calls and chose the same tier mix (haiku 4, sonnet 4, opus 2), which matches the intended ladder row for every task (inventory and extract: haiku; fidelity and lens: sonnet; gate: opus). On these five tasks the instrument is at ceiling for B, C and D, so it cannot separate words-only from plugin-only from both; harder or more ambiguous tasks, where the right answer is not the obvious ladder row, would be needed for that.
- The gate never fired on an orchestrator-level call in the 40 pilot sessions (0 denials). The deny path was exercised only by the instrument probe, where the prompt told the orchestrator to omit the model.
- Skill invocation differed by setup: C 10 of 10, D 3 of 10, A and B 0 of 10 (A and B cannot invoke the plugin's skill since the plugin is absent; the 0 shows no other skill was used). In D the steering text apparently substituted for reading the skill in 7 of 10 sessions while the named-model rate stayed at 10 of 10. This is a count over 10 runs, not an effect estimate.
- Effort was set on 9 of 10 first calls in C and D (one `extract` session in each omitted it) and 10 of 10 in B. In two smoke-test sessions with the plugin loaded the orchestrator remarked that the Agent schema has no `effort` parameter, yet it set effort in most other sessions; I did not verify the schema and treat the remark as unreliable.
- Variability is dominated by the `gate` task, where the opus worker explores heavily and sometimes launches nested subagents: per-session cost ranged from $0.08 to $1.26, and the gate rows account for about half of the spend. Per-setup mean cost differences ($0.25 to $0.40) are inside that spread.
- Nested Agent calls by workers occurred in 5 of 40 sessions, all in the `gate` task (C 2, D 2, B 1). They carried an explicit model in C and D and none in B. The rates above use the orchestrator's own calls only; the `tool_used` graders count nested calls too, which is the one place a grader and the orchestrator-level rate legitimately differ (5 of 320 verdicts under the orchestrator-only rule).

## Problems and surprises

1. **Fixture reads failed on the first smoke run.** The child runs in `dontAsk` mode with an empty working directory, so the worker's `Read`/`Glob`/`Grep` on `$VALIDATION_FIXTURE` were denied (the orchestrator then reported the task could not be done). `--allow-tools "Read(//C:/.../fixture/**)"` did not help. `context.add_dirs` works but accepts only directories inside the case directory. Resolution: `make-cases.js` copies the fixture into `cases/<case>/fixture/` (gitignored by `trials/.gitignore`) and the prompt names that copy, so the prompts' paths are `<plugin repo>/evals/validation-program/trials/cases/<case>/fixture/...` rather than the snapshot path in the brief. The path therefore contains the case name (including `words` or `nowords`) and the plugin's repo name. I did not test whether either leaks into behavior.
2. **Backslash loss in my own tooling.** The first generated graders had lost their regex backslashes (`"model"s*:`) because of how I passed the source through the shell; caught by reading the generated files, fixed with `String.raw`. The pilot's 320 of 320 grader-versus-parser agreement confirms the regexes in `cases/` behave as intended.
3. **Graders count nested worker calls.** The first parser compared graders against orchestrator-level calls only and showed 5 mismatches; all were worker-made nested Agent calls. The analyzer now reports agreement under three counting rules (every call: 320 of 320; orchestrator-level only: 315; orchestrator-level and allowed: 315).
4. **Kept temp directories.** `--keep-temp` leaves each run's directory in `%TEMP%` as `claude-eval-*`, with a warning that the plugin-written parts cannot be sealed on Windows. I read only `out/` and `config/` from them (the analyzer's `collect` copies only transcript JSON and JSONL and the ledger, never the workspace or `.claude.json`) and did not delete the directories; they remain for the orchestrator to remove with the `Remove-Item -Recurse -Force -LiteralPath` command the warning prints.
5. **Tool naming.** The child's init tool list shows the delegation tool as `Task`, while tool calls in the transcript are named `Agent`; the graders and the parser both key on `Agent`.
6. **No harness errors, no rate-limit hits, no cost-ceiling hits.** All 40 pilot sessions completed with `error: null`; the invocations cost $6.11 and $6.28 against the $8 ceiling each. Total spend for everything run, by `costUsd`: about $15.12 of the $40 ceiling (smoke runs 1.97, effort and system-prompt diagnostics 0.35, denied-call and Workflow probes 0.41, pilots 12.39).
7. **Cost estimates are list-price.** `costUsd` is a list-price estimate, not billed usage. The workflow probe's figure may exclude the background workflow worker (one `claude-haiku-5-5` turn), which would be negligible.

## Unverified, labeled as assumptions

- Assumption: the plugin's gate fired on every orchestrator Agent call in C and D. The denial probe shows the hook is live in the same configuration, and a ledger exists in the kept runs, but I did not reconcile ledger rows against calls for the pilot.
- Assumption: `append_system_prompt` reaches the main suite's `words` cases the same way it reached the canary case in the separate diagnostic plugin. The 10 of 10 versus 0 of 10 named-model split between B and A is consistent with that, but I did not read the child's system prompt in the main suite.
- Assumption: the `medium` effort the hook reports is the effort the model actually ran at; I know only what Claude Code reports to hooks.
- Not run: any xhigh pilot, any setup with more than 2 runs per case, any judge-graded quality check of the subagents' answers.
