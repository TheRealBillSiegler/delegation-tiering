## Scoring rules I applied (interpretations, stated before the numbers)

- **First and final delegation:** the first Agent call or Workflow launch at orchestrator level, and the last such call that was not denied. Calls made by workers are not scored (they are counted: 17 sessions had one).
- **Denied:** a tool result that begins `PreToolUse:<Tool> hook error` and names the explicit-model rule. Matching the phrase alone is wrong, because subagent reports quote it (my first parser did this and produced false denials; fixed before any number below).
- **Model:** an omitted model scores as `opus` (protocol). `inherit` also scores as `opus`.
- **Model agreement** is judged on the model alone. **Effort agreement** is the effort being inside the label's band for the chosen model (the union of bands when the chosen model is not in the label); below the band is reported separately, above does not agree. An omitted effort scores as `xhigh`, the session effort. The protocol states this only for an omitted model; extending it to an omitted effort is my reading, and it decides most of the effort result (see Observations).
- **Workflow launches:** every `agent()` call site is located in literal-blanked text (the gate's `blankLiterals`, copied), its argument list is closed by a balanced-paren scan, and `model:` and `effort:` literals are read from the original text at the matched offsets (a string bound once by `const` is resolved; an options object passed by name is looked up). **Role rule for T19 and T20:** the call site that appears last in the script text is the verifier or merger (the call made after the fan-out); every earlier site is a fan-out call. A launch agrees on model only if it has at least two sites, every site names a model, every fan-out tier is in the fan-out label and the last site's tier is in the gate label; effort agrees under the same roles and requires every site to name an effort. A plain Agent call on a workflow task scores as a non-match. Batch 1 had 2 first-delegation launches (T19, one B and one D), both with two sites and no unresolved expressions.
- **Named-model (endpoint 2):** the Agent call has a non-empty `model`; a launch needs a model literal on every site.
- **Shares:** per task and setup, the share of non-errored runs (non-delegating runs count as non-match; there were none). Tasks missing either cell of a contrast drop out of that contrast's test.
- **Secondary family:** the protocol names the family but not every contrast, so I fixed ten before computing: effort agreement D vs B; model agreement C vs B; over- and under-provisioning for D vs B and C vs A; gate denials D vs C; Skill invocation D vs C; delegation rate D vs B and C vs A. Holm applies across the ten. Over- or under-provisioning means the tier is above the highest or below the lowest tier the label accepts.

## Observations the numbers support (small n, descriptive)

With one run per cell and 13 tasks, a single task decides the sum, which is why the exact p is 1.0 and the interval reaches +0.231.
- **Plugin only (C) agreed on 16 of 16** and named a model on 16 of 16, so the plugin alone matched or beat the text on this partial sample (C vs B: +0.091, Holm p 1.0).
- **Effort is almost never named on an Agent call at xhigh:** 0 of 56 first Agent delegations set `effort`, in every setup; the two workflow launches did. The Agent tool's `effort` description, as quoted in the pilot's transcript, tells the model to set it only when the user or instructions explicitly ask; whether that text was present in batch 1's tool schema I did not verify (the batch-1 transcripts I searched do not carry it). Under my scoring rule an omitted effort is `xhigh`, so effort agreement is mostly whether the label's band contains `xhigh`, and the effort rows say little about the plugin.
- **Over-provisioning is mostly the scoring rule, not a choice.** A's 8 over-provisioned runs are omitted models scoring as opus on haiku and sonnet tasks; the C vs A difference (-0.533, raw p 0.0078, Holm p 0.078) is that artifact.
- **The gate did not deny any orchestrator-level delegation** in batch 1 (0 of 63 sessions). It denied nested worker calls in 5 sessions (C 2, D 3); those calls are not scored. The delegation-tiering skill was invoked in 16 of 16 C runs and 14 of 14 D runs, against 3 of 10 D runs in the pilot (at medium effort).
- **Workflow tasks are thinly covered:** T19 has a B and a D cell only (both chose sonnet for the verifier, label opus, so both disagree); T20 has no scored cell, because its batch-1 pair timed out and its with-text pair was never started.

Per-setup means differ mostly because the missing cells differ by setup, so they are not comparable across setups without a task-balanced reading; the per-task table is.

## Deviations from the protocol

1. **Partial execution (cost rule).** Batch 1 stopped at 63 of 80 sessions on the $60 ceiling; batches 2 and 3 were not run because the projection ($0.969 x 240, about $232) exceeds $150. The registered 3 runs per arm and 20-task comparison were therefore not obtained. I did not run the 17 unstarted sessions as a top-up, because that would exceed the $60 per-batch ceiling.
2. **Case directory grouping.** Cases sit in `cases-full/g1` to `g5` (8 each) rather than flat. The harness passes a deny list on the command line that names every sibling of every ancestor of the case directory; with 40 flat siblings the plugin arm's child failed with `ENAMETOOLONG` at the 32,767-character limit (observed in the first smoke test, plugin arm of both cases; the no-plugin arms ran). Grouping cut the siblings per case from 39 to 11. Directory names remain neutral. The key (outside the repo) records each case's group.
3. **Output location.** `run-eval.sh` writes under `validation-data/trials/<label>`; I passed the label `../trials-full/<name>` so results land in `trials-full/` without editing the script.
4. **Cost ceiling override.** `run-eval.sh` hard-codes `--max-cost-usd 8` before `"$@"`. A probe (`--max-cost-usd 0.03`, two runs) stopped after the first run, confirming my later flag wins. That probe cost $0.093.
5. **`--case` takes no character classes**, so the smoke test used one invocation per case.
6. **Smoke test shape.** Case c35 (T02, with text) and c33 (T19, no text). The first pass ran both arms, but the plugin arms failed on the command-line length (deviation 2). After regrouping I re-ran only the plugin arm of each (`--ablation none`). The first pass's no-plugin arms (kept in `smoke-old/`) are valid but come from the flat layout. Smoke and probe spend was $4.81 in total (limit $10). Parser and graders agreed on all smoke verdicts.
7. **Timeouts are excluded** from denominators (the protocol is silent on harness errors); the sensitivity run above shows the effect.
8. **Verbatim prompts keep the table's backticks** (the markdown code formatting around paths and flags), since the protocol's text includes them.
9. **Fixture directory name** is `fx` (the protocol says only "a neutral directory name"). Prompt paths contain the repo name `delegation-tiering-validation` and `cases-full/gN/cNN/fx`, the same in every condition.
10. **Secondary-family contrasts** are my choice (listed under Scoring rules); the protocol names the family's members but not the contrasts for the per-setup items.
11. **The effort scoring extension** (omitted effort scores as the session effort) and the **workflow role rule** are my readings, stated above.
12. **Total spend** was $65.84 by costUsd ($61.03 batch 1 plus $4.81 smoke and probe), under the $160 ceiling.

## Post-hoc mechanism check (not part of the registered analysis)

Run by the orchestrator on 2026-10-09 after batch 1, to explain why no first Agent call in batch 1 set `effort` when 56 of 90 Agent calls in the pilot had. Claude Code records each session's Agent tool definition in its transcript. On Claude Code 2.1.295 the definition carried an `effort` parameter in 72 of 72 pilot transcripts that record it (orchestrator at `medium`) and in 0 of 129 batch-1 transcripts (orchestrator at `xhigh`). Two one-session probes on case `c09` with the plugin loaded separated the session's effort level from the Workflow grant: at `xhigh` without `--allow-tools Workflow` the definition had no `effort` parameter, and at `medium` with the grant it had one. The probes cost $0.28 together. On this version, then, an `xhigh` session's Agent tool offers no `effort` parameter, so every direct Agent worker in batch 1 ran at the session's `xhigh`. The orchestrating session that ran this program (VS Code extension 2.1.292, `xhigh`) did offer the parameter, so the cause is either the version or the surface; these runs cannot separate the two.
